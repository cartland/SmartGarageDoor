# Play Store assets

This skill is the procedure for refreshing the **store listing** images. The
release workflows only ship the AAB + `whatsnew/`, never images.

**Screenshots** are uploaded by the `Play Listing Images` workflow (see below).
The **icon** and **feature graphic** are still a manual Console step.

Curating which images go live stays a human decision reviewed in a PR — the
workflow publishes what is committed under `distribution/playstore/`, it does
not choose or generate anything.

## The two places assets live

| Location | What | Committed? |
| --- | --- | --- |
| `MobileGarage/screenshots/store/` | **Generated** — everything the generators produce (all candidates) | Yes |
| `MobileGarage/distribution/playstore/` | **Curated** — the exact subset we keep in sync with the live store | Yes |

Both are committed. Generators **only write to the generated dir**;
`distribution/` is updated by hand: you copy the images you actually want, open a
PR, then upload them in Play Console. Never point a generator at `distribution/`.

## Generators

**Screenshots regenerate automatically** as part of the normal screenshot update
— `./scripts/generate-android-screenshots.sh` (the `update-android-screenshots`
skill) runs `scripts/generate-store-screenshots.py` right after the README
framing step. You usually don't run the screenshot generator by hand.

The icon + feature graphic have their own generator (they come from an SVG, not
the screenshot pipeline):

```bash
# Icon (512) + feature graphic -> screenshots/store/.  Also regenerates the
# in-app launcher mipmaps in androidApp/.../res/ (committed app code, see below).
bash MobileGarage/distribution/playstore/generate.sh

# Screenshots only — normally run via the screenshot pipeline above, but can be
# run directly. Composes committed framed shots + tablet reference renders (no
# rendering), so it works even though local Layoutlib render is blank.
python3 scripts/generate-store-screenshots.py
```

Both write to the committed `MobileGarage/screenshots/store/` dir, which also
gets a `README.md` gallery (regenerated by the screenshot generator) so the
latest set is always viewable on GitHub:

```
screenshots/store/
  README.md                <- gallery of everything below
  icon-512.png
  feature-graphic-1024x500.png
  phoneScreenshots/        01..06  (1544x2744, 9:16)
  sevenInchScreenshots/    01..04  (~3700x2100 / 3584x2016, 16:9)
  tenInchScreenshots/      01..04  (~3734x2100, 16:9)
```

- **Phone** — the framed Pixel shots flattened onto white at their native ratio
  (~2.12:1). Play **accepted** this ratio (uploads approved 2026-06-11), so it's
  left native — do not pad to 9:16.
- **Tablet** — wrapped in a programmatic tablet bezel (`frame_tablet`) centered on
  a white **16:9** canvas (3840×2160 for 7-inch, 4494×2528 for 10-inch). Polished
  and Play-compliant.

All PNG, < 8 MB, sides within range.

## Updating the store — step by step

1. **Regenerate** — the screenshots refresh with the screenshot pipeline; run
   `generate.sh` if the icon/feature changed. (A true UI refresh of the
   screenshot *sources* needs a working env / CI — see _Refreshing screenshot
   sources_.)
2. **Review** the generated images in `MobileGarage/screenshots/store/` (open
   its `README.md` for the gallery).
3. **Copy the ones you want** into `distribution/playstore/`:

   | Copy from staging | Copy to distribution | Play Console field |
   | --- | --- | --- |
   | `icon-512.png` | `distribution/playstore/icon-512.png` | Main store listing → App icon |
   | `feature-graphic-1024x500.png` | `distribution/playstore/feature-graphic-1024x500.png` | Main store listing → Feature graphic |
   | `phoneScreenshots/*.png` (2–8) | `distribution/playstore/screenshots/phoneScreenshots/` | Phone screenshots |
   | `sevenInchScreenshots/*.png` (≤8) | `distribution/playstore/screenshots/sevenInchScreenshots/` | 7-inch tablet screenshots |
   | `tenInchScreenshots/*.png` (≤8) | `distribution/playstore/screenshots/tenInchScreenshots/` | 10-inch tablet screenshots |

   You don't have to copy all of them — pick the subset you want live. Phone
   needs 2–8; tablets are ≤8 and only required if targeting large screens.
   Wear screenshots live in `distribution/playstore/wear/` (≤8, ≥384px;
   the fixture renders 454×454). Name curated files with a numeric prefix
   (`01_closed.png`) — Play shows screenshots in upload order, and the
   uploader sorts by filename, so filename order IS the story a visitor sees.
4. **Open a PR** with the new `distribution/playstore/` images. This is the
   record of what's live in the store.
5. **After merge, run the `Play Listing Images` workflow** (dry run, then
   `apply=true`) for screenshots. Icon and feature graphic are still uploaded
   by hand in Play Console (Store presence → Main store listing).

## Important distinctions

- **Launcher icon ≠ store icon.** `generate.sh` writes the in-app launcher
  mipmaps into `androidApp/.../res/mipmap-*` — that's app code, it ships in the
  AAB automatically on the next `release-android`, and is NOT a manual upload.
  The 512 `icon-512.png` is the separate *store listing* icon and IS a manual
  upload. Both come from the same `src/icon.svg`.
- **Aspect ratio.** Play's hard limit is "longest side ≤ 2× shortest side"; the
  generators pad to an exact 16:9 / 9:16 to stay safely inside that and match
  the nominal requirement.

## Refreshing screenshot sources

Phone screenshots come from `MobileGarage/screenshots/framed/` and tablet
screenshots from the committed AGP reference PNGs
(`android-screenshot-tests/.../reference/.../ScreensScreenshotTestKt/`). Those
are regenerated by the normal screenshot pipeline
(`./scripts/generate-android-screenshots.sh`), which **renders blank on this
Mac** (see root `CLAUDE.md`). So a true UI refresh of the *sources* needs a
working environment / CI; `generate-store-screenshots.py` itself only re-composes
whatever sources are currently committed.

## Uploading screenshots: automated (`Play Listing Images` workflow)

**Screenshots** no longer need a Console visit. `.github/workflows/play-listing-images.yml`
syncs the curated sets to the live listing via the Play Developer API,
reusing `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`.

```bash
# 1. Dry run FIRST. Uploads everything into a Play edit, then abandons it.
gh workflow run play-listing-images.yml -f image_types=wearScreenshots -f apply=false

# 2. Publish.
gh workflow run play-listing-images.yml -f image_types=wearScreenshots -f apply=true
```

`image_types` is comma-separated; valid values are `wearScreenshots`,
`phoneScreenshots`, `sevenInchScreenshots`, `tenInchScreenshots`. Only the
types you name are touched — the rest of the listing is left alone.

Why the dry run is worth doing every time: Play edits are **transactional**, so
`apply=false` exercises the entire path — auth, the "Edit store listing"
permission, image dimensions, count limits — and then discards the edit. It is
a real rehearsal, not a simulation.

Two safety properties are enforced in code (`.github/scripts/lib/listing-images.mjs`,
unit-tested):

- **An empty set is refused**, never treated as a no-op. Play has no "set"
  operation, so syncing is `deleteall` + upload; a typo'd path that matched
  zero files would otherwise silently wipe that section of the live listing.
- **Only the curated tree is eligible.** The generated staging tree has a
  `wear/` directory too, so matching on directory name alone would publish
  un-curated candidate shots.

**Still manual:** the store `icon-512.png` and `feature-graphic-1024x500.png`.
They are single-image fields rather than ordered sets, they live outside the
per-imageType directory layout, and they change far less often than
screenshots. Upload those in Console per the table above.
